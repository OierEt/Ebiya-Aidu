## Adding or changing pages
- **Cache busting (mandatory):** every HTML file loads `css/style.css`, `js/theme.js`, `js/lauburu.js` and `js/nav.js` with `?v=<version>`. GitHub Pages lets browsers cache files for about 10 minutes, so without a new version the visitor can get new HTML with an old CSS or JS and the site looks broken (this already happened once). Whenever any CSS or JS file changes, set a new version in all HTML files: `sed -i -E 's/\?v=[0-9a-z]+/?v=NEWVERSION/g' *.html eu/*.html`.
- Header, nav, language switch and footer are repeated in every HTML file. A nav change must be applied to all 10 files (every html file, now including `play.html`).
- The language switch in each page links to the same page in the other language (`eu/x.html` from the root, `../x.html` from `eu/`).
- A new page is a copy of an existing page of the same language, plus a nav entry in all pages of both languages.
- Check every `href` and `src` resolves to an existing file before pushing.

- Shared basket counter: Supabase project `cqwblkgghzvonxsazasm` (EU), the first version used a table `counters` (`backend/counter-setup.sql`, now unused). Everything comes from the table `shots` (`backend/shots-setup.sql`, then `backend/shots-update.sql`, which adds `speed_raw` and the function `shot_stats()`); the browser can only read it, call `record_shot(...)` and `shot_stats()`. The Play page totals (2×, 3×, points, throws, % scored) come from `shot_stats()`. `js/lauburu.js` has `DB_URL` and `DB_KEY` (the public publishable key, safe to publish; never put the secret/service_role key in the repository) and sends one anonymous record per throw (`record_shot`, table `shots` from `backend/shots-setup.sql`: made, points, distance, release position as window fractions, direction, speed, flight time, window size, touch; throws slower than `MIN_SHOT_SPEED` (60 px/s) and throws with the hoop hidden are not recorded; a throw is saved when it scores, when the ball comes to rest, or when the ball is grabbed again after 0.6 s of flight; `speed` is capped at `MAX_THROW` 2400 px/s and `speed_raw` keeps the real value; the hoop is fixed at the right edge at 36vh so `release_x/release_y` (fractions of the window) are comparable between screens, while `dist`/`hoop_dx`/`hoop_dy` are real pixels). The Play page says this to visitors; keep that notice if the data change. Charts (`js/charts.js`, only on `play.html`, plain SVG coloured with CSS variables, one column of cards, reads up to the last 5000 rows of `shots` including `vw`, `vh`, `hoop_dx`, `hoop_dy`, `created_at`: screen-shape filter All/Landscape/Portrait, summary, release positions with the hoop drawn as on screen (toggle: window fractions / real pixels from the hoop), accuracy heat map by position, distance histogram, regression of scored vs distance (logistic or linear toggle, metrics: odds ratio, p, McFadden R², AUC, accuracy, 50% distance / slope, R², r), speed histogram with the 2400 cap line, speed vs distance, direction as bars or radar, rolling accuracy over time; histograms have a bin-width select and a count / % within each bin (scored vs missed) toggle; position plots stretch every screen to the same box because x/y are window fractions) are built; `js/play.js` (only on `play.html`) shows the totals and the visitor's own score. The sandbox cannot reach Supabase, so test with a mocked `fetch` and ask the owner to check the real thing.

A hoop (`.hoop`) is fixed at the right edge at 36vh and a score box (`.score`) at the bottom right; both are created by the script, not written in the HTML. A basket from far (distance greater than 30% of the window diagonal) counts 3, otherwise 2. The score is kept in `localStorage` (`lauburuScore`); the visitor can hide the hoop with the button in the score box. Gravity, bounce and throw limits are constants at the top. Before changing the physics, test it in a real browser (for example puppeteer-core with the installed Chrome) by throwing the ball and checking that near shots score 2, far shots score 3 and weak throws score nothing.
